# mysql_to_pg skipped cases

This file records the `random_test.cpp` workload cases that were not fully converted from MySQL syntax/semantics to PostgreSQL yet, plus the reason for each decision.

## Already adapted in this round

- Connection loss detection in `execute_sql()`
  PostgreSQL error handling now records SQLSTATE and treats SQLSTATE class `08` plus shutdown states `57P01/57P02/57P03` as lost-connection cases.
- `USE db`
  Replaced with `SET search_path TO pstress`.
- `CREATE/DROP DATABASE test`
  Replaced in preload flow with `DROP SCHEMA IF EXISTS pstress CASCADE`, `CREATE SCHEMA pstress`, and `SET search_path TO pstress`.
- `AUTO_INCREMENT`
  Replaced in column definition with `GENERATED BY DEFAULT AS IDENTITY`.
- `REPLACE`
  PostgreSQL has no direct equivalent. Current behavior uses `INSERT ... ON CONFLICT ... DO UPDATE` when a primary key exists, otherwise it falls back to plain `INSERT`.
- `INSERT ... IGNORE`
  PostgreSQL has no direct syntax equivalent without conflict-target design. Current behavior removes `IGNORE`.
- `OPTIMIZE TABLE`
  Current PostgreSQL substitute is `VACUUM ANALYZE`.
- `ANALYZE TABLE`
  Current PostgreSQL substitute is `ANALYZE`.
- `CHECK TABLE`
  Current PostgreSQL substitute is a synthetic success probe used to keep the control flow moving. It is not a physical table-check equivalent.
- `DROP INDEX`
  Replaced with `DROP INDEX IF EXISTS`.
- `RENAME INDEX`
  Replaced with `ALTER INDEX old_name RENAME TO new_name`.
- `ADD INDEX`
  Replaced with `CREATE INDEX name ON table (...)`.
- `MODIFY COLUMN`
  PostgreSQL path now covers ordinary `ALTER COLUMN ... TYPE ...`, identity add/drop, and generated-column rebuild via `DROP COLUMN` + `ADD COLUMN`. Default rewrites and full MySQL parity are still not fully covered.
- metadata file format
  New metadata now uses neutral storage keys such as `storage_engine`, `storage_layout`, `storage_tablespace`, `storage_encryption`, `storage_compression`, `storage_block_size`, and `length`. Loader keeps backward compatibility with old MySQL-shaped keys like `engine`, `row_format`, `tablespace`, `key_block_size`, and `lenght`. The in-memory `Table` storage fields were renamed to the same neutral naming scheme.
- help and option naming
  User-facing help text was rewritten toward neutral/PostgreSQL wording, and several long options were renamed to neutral names such as `server-option`, `server-option-file`, `set-server-variable`, `undo-tablespace-count`, `undo-tablespace-sql`, `no-generated-columns`, and `alter-tablespace-*`. Legacy MySQL-era long-option aliases are still accepted for compatibility.

## Disabled because PostgreSQL does not support the same feature model

- `ALTER TABLE ... ENCRYPTION`
  PostgreSQL does not expose a MySQL-style table encryption clause.
- `ALTER TABLE ... COMPRESSION`
  PostgreSQL does not support MySQL InnoDB table compression syntax.
- `ALTER TABLE ... ENGINE=InnoDB`
  PostgreSQL has no pluggable table engine syntax equivalent.
- `ALTER TABLE ... DISCARD TABLESPACE`
  PostgreSQL does not support this MySQL/InnoDB tablespace lifecycle.
- `ALTER TABLESPACE ... ENCRYPTION`
  PostgreSQL tablespaces do not use this encryption syntax.
- `ALTER TABLESPACE ... RENAME`
  Semantics differ and current workload assumes MySQL general tablespaces.
- `ALTER INSTANCE ...`
  PostgreSQL has no MySQL `ALTER INSTANCE` family for redo/key rotation/keyring operations.
- `CREATE/DROP/ALTER UNDO TABLESPACE`
  PostgreSQL does not have MySQL undo tablespaces.
- keyring/gcache/redo log key rotation cases
  MySQL/PXC specific features, no `libpq` SQL equivalent.
- MySQL server variable randomization in `set_mysqld_variable()`
  Current SQL is still `SET SESSION/GLOBAL` over MySQL-oriented variable names. PostgreSQL GUCs require a separate supported-variable allowlist.

## Still partially MySQL-shaped and should be revisited

- `SHOW`/`@@` server probes
  Only `@@innodb_page_size` was mapped to `show block_size`. Remaining MySQL metadata checks are guarded or disabled, not fully redesigned.
- generated column syntax
  PostgreSQL generated columns now use stored generated columns only, with explicit casts/`CASE` handling for PG type rules. This is no longer a direct MySQL string translation, and expression coverage is still narrower than full MySQL behavior.
- `ADD COLUMN ... AFTER col`
  PostgreSQL does not support column position changes. Current PostgreSQL path skips `AFTER`.
- fake `CHECK TABLE` replacement
  This preserves control flow only. It does not validate heap/index corruption like a real low-level check would.
- `REPLACE` semantics are still only approximate
  MySQL `REPLACE` is delete-then-insert. The PostgreSQL port now uses an upsert on primary-key conflicts, which is closer than plain `INSERT`, but it is still not identical to MySQL `REPLACE`.
- partial `MODIFY COLUMN` replacement
  PostgreSQL often needs multiple subcommands for one logical column change. The current port now handles the common `ALTER COLUMN ... TYPE ...` path, identity add/drop, and generated-column rebuilds, but it still does not implement full default-expression rewrite parity with MySQL.
- partition behavior is only partially ported
  PostgreSQL declarative partition creation is now used for new partitioned tables, and basic DML/maintenance can target child partitions. Dynamic maintenance for `RANGE`, `LIST`, and `HASH/KEY` now has a PostgreSQL-native path, but `HASH/KEY` uses a rebuild-and-reinsert strategy rather than a lightweight in-place repartition, and full metadata evolution is still pending.

## Why some cases were skipped instead of force-converted

There are three different reasons:

1. PostgreSQL has no equivalent feature at all.
2. PostgreSQL has an equivalent capability, but not via the same SQL syntax, so the generator logic must be redesigned instead of string-replaced.
3. The current workload assumes MySQL metadata, storage-engine behavior, or partition internals, so a safe PostgreSQL port needs schema-generation changes first.

## Recommended next steps

1. Rebuild the table/index DDL generator around PostgreSQL-native syntax.
2. Replace MySQL variable randomization with a PostgreSQL GUC allowlist.
3. Rework partition support as PostgreSQL declarative partitioning.
4. Decide whether `REPLACE` should become `INSERT`, `INSERT ... ON CONFLICT DO NOTHING`, or `INSERT ... ON CONFLICT DO UPDATE`.
5. Replace the synthetic `CHECK TABLE` with a PostgreSQL-specific health check strategy.
